## 1. 게임 개요

### 한 줄 정의

> 정체를 가린 실제(현재는 합성) 과거 거래일 차트를 읽어 전쟁 자금을 만들고, 그 돈으로
> 일자형 타워디펜스 13웨이브를 막아 지역을 점령하는 게임.

| 항목 | 값 |
|---|---|
| 장르 | 차트 트레이딩 × 레인 타워디펜스 |
| 플랫폼 | 웹 (데스크톱 우선) · Vite + TypeScript · Canvas 2D |
| 1스테이지 길이 | **390초** (= 1분봉 390개 × 1,000ms). 배속 1x 기준 6분 30초 |
| 웨이브 | 13웨이브 × 30초 (준비 5초 + 교전 25초) |
| 세션 길이 | 시작 게이트 → 지역 선택 → 플레이 390초 → 연장(최대 30초) → 정산 |

`src/market/types.ts` `BARS_PER_DAY = 390` · `MS_PER_BAR = 1000` · `STAGE_DURATION_MS = 390_000`
`src/combat/constants.ts` `WAVE_COUNT = 13` · `WAVE_DURATION_MS = 30_000` · `WAVE_PREP_MS = 5_000`

### 코어 루프

```
차트 예측 → 포지션 진입 → 청산 → 골드
   ↑                                 ↓
AUM 드롭 ← 적 처치 ← 방어 ← 타워·유닛·스킬 구매
```

### ★ 차트와 전투가 맞물리는 방식 — 이 게임의 핵심

**두 시스템은 같은 시계를 공유한다.** 리플레이 390초와 전투 13 × 30초 = 390초가
**정확히 같다**(`constants.ts` `WAVE_DURATION_MS` 주석). 그래서 "차트를 보는 시간"과
"막는 시간"이 같은 시간이며, 둘 중 하나를 선택해야 한다.

맞물림은 네 갈래다.

| 방향 | 연결 고리 | 코드 |
|---|---|---|
| 차트 → 전투 | 청산 대금이 골드가 되고, 골드로만 타워·유닛·스킬(S-01/S-02)을 산다 | `src/position/trade.ts` `closePosition` |
| 전투 → 차트 | 적을 잡아야 AUM(매매 원금)이 들어온다. **AUM이 늘어나는 유일한 경로다** | `src/app/session.ts` `stepCombatFrame` |
| 전투 → 차트 (역방향 소모) | 스킬 `S-03`은 AUM을 태운다 — 실드를 켤수록 굴릴 돈이 준다 | `src/combat/actions.ts` `castSkill` |
| 차트 → 화면 | 시장 상태가 전장 **날씨**로 표시된다(폭우·상승기류·안개·정전) | `src/weather/classify.ts` ※ 배선 미완, §13 |

되먹임의 강도는 지역마다 다르다. R1은 세션 총 투입액의 **49%**가 전투 드롭에서 오지만
(1,950 / 3,950), R3는 **22%**뿐이다(1,950 / 8,850). 즉 R1은 "방어가 무너지면 매매도 마른다"가
가장 강하고, R3는 "쥐고 시작한 자본을 잃지 않는 것"이 지배적이다.

또 하나: **추가 매수(물타기)가 방어를 얇게 만든다.** 손실 중 추가 매수하면 평균 단가가
현재가 쪽으로 당겨져 강제 청산선이 밀리지만(버티기 성공), 그만큼 골드로 바꿀 AUM이
사라진다. 이 트레이드오프가 매매 판단을 전투 판단으로 직결시킨다
(`src/position/trade.ts` `addToPosition` 주석).

## 2. 플레이 흐름

```
[시작 게이트]  →  [지역 선택]  →  [준비 5초]  →  [웨이브 1~13]  →  [장 마감]  →  [연장]  →  [정산 화면]
```

### 2-1. 시작 게이트 (`src/app/start-gate.ts`)

프레임 루프가 **한 번도 돌지 않는 정지 상태**로 마운트된다.
클리어 보상(정체 공개)을 미리 걸어 동기를 만든다.

**진입 3종** (`src/app/challenge.ts`):

| 진입 | 시드 | heat | 모드 |
|---|---|---|---|
| **[스테이지 시작]** | 현재 값(기본 1) | 진행도의 점령 수 | `free` |
| **[오늘의 챌린지]** | **오늘 날짜**(`2026-08-03` → `20260803`) | **1 고정** | `daily` |
| **시드 직접 입력** | 입력값 (`20260803` / `2026-08-03` 둘 다 허용) | **1 고정** | `seed` |

`generateChartSet(seed)`가 결정론적이라(mulberry32) **시드만 같으면 문자 단위로 같은 차트**다.
실데이터가 없어도 "전 유저가 같은 판을 푼다"는 경쟁 구조는 지금 성립한다 — 실데이터가 주는
것은 경쟁이 아니라 **정체성**이며, 둘은 분리돼 있다.

> **★★ 챌린지는 heat를 1로 고정한다 ★★** 진행도가 붙으면서 `heat = 1 + 점령 수 × 0.04`가
> 살아났다. 그대로 두면 **같은 시드라도 진도가 앞선 사람이 적 HP 8% 높은 판**을 받아,
> 성적 비교가 성립하지 않는다. `CHALLENGE_TERRITORIES = 0`이 그 불변식이며 테스트가 고정한다.

### 2-2. 지역 선택 (`src/app/region-select.ts`)

R1 여의도 / R2 판교 / R3 울산 카드 3장. 각 카드는 `STAGES`에서 읽은
**시작 AUM · 시작 골드 · 목표 수익률 · 필요 지출**을 노출한다.
`Esc` 또는 [← 타이틀로]로 게이트 복귀. **여기서 처음으로 프레임 루프가 돈다.**

> 진행도 저장이 없어 세 지역 모두 잠금 해제 상태다(`locked: false` 고정).

### 2-3. 준비 5초 (`src/combat/wave-clock.ts`)

- 적이 **스폰되지 않는다.** 타워를 세우는 시간이다.
- **차트는 계속 흐르고 매매도 가능하다** — "예고를 보고 미리 산다"는 코어 루프의 자리.
- 시작 골드 120 G는 기본 포탑 정확히 1기 값이다. **2기째 자금은 첫 청산 이익에서만 나온다.**
- `Space` 또는 [바로 시작]으로 즉시 종료.

### 2-4. 웨이브 (교전 25초)

- 적은 교전 구간 경과 비율에 비례해 순차 스폰된다(`simulate.ts` `spawnDue`).
- 웨이브 시작 시 **기본 수입**이 골드로 들어온다.
- 적 1체 처치마다 **AUM 드롭**.
- 본진 HP 100. 적 1체 누출 = −6 (보스는 −18).
- 준비 구간은 매 웨이브 시작 전에 반복된다(주기 30초 = 준비 5 + 교전 25).

### 2-5. 장 마감 (재생 390초 종료)

재생 종료는 **전투 종료가 아니다.** 시계 비대칭 때문에 둘은 같은 사건이 될 수 없다
(`src/app/stage-flow.ts` `decideFrame` 주석). 그래서 재생 종료 시:

1. `marketClosed = true` — 매매 버튼 전부 잠금
2. 열려 있던 포지션 **강제 청산**(`reason: 'stage_end'`) + 골드 비행 연출 소비
3. 연장 시작 — `overtimeRemainingMs = waveDurationMs`(1x 기준 30초)

### 2-6. 연장 → 정산

전투가 `cleared`(13웨이브 방어 완료) 또는 `defeated`(본진 HP 0)에 도달하면 결과 확정.
연장이 소진되었는데도 결론이 안 나면 `unresolved`(방어 미완료 — 자본금 0).

**공개 연출(FR-9)이 정산보다 먼저 온다.** 연출이 끝나야 정산 화면이 뜬다 —
패배해도 보여준다(FR-9.5).

정산 화면은 **스테이지가 끝나는 유일한 경로**다. 무음 리셋 경로는 타입 수준에서 제거됐다.
출구는 [다시](같은 지역·새 시드)와 [지역 선택으로], 그리고 **[결과 카드 저장]**이다.

결과 카드(`src/app/result-card.ts`)는 1200×630 PNG로 굽고 공유 문자열을 클립보드에 넣는다.
**시드가 반드시 실린다** — 받는 사람이 정확히 같은 판을 열 수 있어야 공유의 의미가 있다.
블라인드 규칙상 종목·날짜가 없으므로 정체 자리에는 **지역 + 시드**가 들어간다(실데이터가
붙으면 이 자리가 종목·날짜로 바뀐다). **패배는 등급과 무관하게 `ENEMY_DOWN`**이다 —
자본금 0인데 카드가 금색이면 거짓말이 된다.

| 결과 | 조건 | 자본금 |
|---|---|---|
| `cleared` | 13웨이브 방어 완료 | 정산식대로 지급 |
| `defeated` | 본진 HP 0 | **0** |
| `unresolved` | 장 마감 + 연장 소진, 결론 없음 | **0** |

## 4. 아군 유닛 3종

정체성: `src/combat/identity.ts` `ALLY_IDENTITY` · 수치: `src/combat/constants.ts`
소환 로직: `src/combat/actions.ts` `summonUnit`

세계관 — **"장 마감 후에도 남은 사람들"**. 아군은 사옥을 지키는 쪽이지 적 본진을 치는 쪽이 아니다.

| | `intern` | `analyst` | `trader` |
|---|---|---|---|
| 코드 ID | **A-01** | **A-02** | **A-03** |
| 이름 | **개장벨 사환** | **호가 통신원** | **락업 반장** |
| 역할 | 근거리 | 원거리 | 탱커 |
| **비용** | **30 G** | **60 G** | **90 G** |
| **HP** | **110** | **135** | **470** |
| **공격력**(1회) | **10** | **18** | **17** |
| **공격 주기** | 700 ms | 700 ms | 700 ms |
| **DPS** | 14.3 | 25.7 | 24.3 |
| **사거리** | 0.05 (밀착) | **0.20** | 0.05 (밀착) |
| **이동속도** | 0.05 /초 | 0.05 /초 | 0.05 /초 |
| HP/G | 3.67 | 2.25 | **5.22** |
| DPS/G | 0.48 | **0.43** | 0.27 |

  차등은 비용·HP·공격력·사거리에만 있다.
- 이동속도 0.05/초 = 라인 전체(0→1) 주파에 20초.

### 외형 (`src/sprites/ally.ts`, 스프라이트 `tf-ally-01/02/03`)

| | 실루엣 묘사 |
|---|---|
| A-01 | 놋쇠 **개장벨**을 뒤집어 쓴 최말단 사환 — 값싸고 많고 제일 먼저 죽는다 |
| A-02 | **티커테이프 릴**을 짊어진 신호수 — 풀린 테이프 길이만큼 멀리서 쏜다 |

(`src/design/encoding.ts` `silhouetteShapeFor('ally')`).

### 전술적 용도

**★ 전진 한계선 `UNIT_HOLD_LINE = 0.45` ★**
유닛은 표적이 없어도 x = 0.45를 넘지 않는다. 적이 밀착 사거리(0.05)만큼 앞에서 멈추므로
**실제 교전선은 x ≈ 0.50**이며, 이는 슬롯 4~5 기본 포탑의 사거리 안(0.52 / 0.555)이다.

한계선이 없던 시절 유닛은 적 본진(x=1)까지 걸어가 거기서 요격했고, 그 결과
**타워가 5웨이브 동안 한 발도 못 쐈다.** 타워와 유닛이 더해지지 않고 서로를 대체한 것이다.
전투 시뮬레이터 실측에서 유닛 예산 1,560 G를 추가하면 잔여 HP가 **40 → 16으로 오히려 나빠졌다.**
한계선은 그 구조적 결함의 해법이다.

| 유닛 | 언제 쓰는가 |
|---|---|
| **사환** | 물량으로 적을 세워 두는 용도. 세워 두는 동안 타워 가동률이 오른다 |
| **통신원** | 적이 밀착하기 전 일방적 사격 구간(0.20 → 0.05)을 노린다. 구간 길이는 **적 종류마다 다르다** — 속공 E-01은 2.4초(3회 선타), 탱커 E-03은 4.2초(6회)다. 근접 적이 뚫고 들어오면 급격히 약하다 |
| **반장** | 전열 유지. 거리 동률일 때 **자기 사거리가 짧은 쪽이 먼저 맞는 규칙** 덕에 근접 탱커가 원거리를 보호한다(`mechanics.ts` `nearestInRange` 타이브레이크) |

유닛이 타워보다 골드당 효율이 낮아도(약 5.8 dmg/G vs 타워 목표선 10.5 dmg/G) 존재 이유가 있다:
① **적을 세워 둔다**(그동안 타워가 계속 쏜다) ② **웨이브를 보고 그때 산다**(타워는 미리 지어야 한다).

> **⚠️ 공중 적과는 절대 교전하지 않는다.** 원거리 유닛도 예외 없다(`applyEngagement`는
> `lane === 'ground'`만 필터한다). 공중은 대공 포대 전용이다.

### 스탯 설계 규칙

- **HP는 배수다.** 웨이브 테이블(§5 아래)이 그 웨이브의 HP **예산**을 정하고, 종류가 그 예산을
  나눠 갖는다: `개체 HP = baseHp[w] × heat × hpMultiplier`. 지역 계수(R2 ×1.20 / R3 ×1.30)와
  heat가 종류 차등 **위에** 그대로 곱해진다.
- **지상 배수 합이 정확히 3.0, 공중이 2.0이다.** 그래서 `0.35a + b + 1.65c = a+b+c ⇔ a = c` —
  **속공과 탱커를 같은 수로 넣으면 웨이브 HP 예산이 보존된다.** 웨이브 구성은 이 항등식을
  기준선으로 삼아 **의도적으로만** 벗어난다(아래 구성 표).
- **완주 시간의 평균을 기준선에 맞춘다.** 타워가 개체에 넣는 총 피해는 사거리 체류 시간
  ∝ `1/speed`에 비례하므로, 속도의 산술평균이 아니라 완주 시간의 평균을 맞춘다:
  지상 (16+24+28)/3 = 22.7초(기존 22) · 공중 (14+19)/2 = 16.5초(기존 16).
- **사거리는 전 종 0.05 고정이다.** 0.05를 넘는 적은 유닛 전진 한계선(0.45)에 선 유닛을
  **반격 불가능한 거리에서 영원히** 때린다 — E-02에 긴 사거리를 주는 "방패" 안이 이 이유로 폐기됐다.
- **공중의 `damage`는 죽은 값이다.** 공중은 유닛과 교전하지 않으므로(FR-6.2) 공중의
  "피해가 크다"는 **누출 피해**로만 표현된다.

| 항목 | 지상 공통 | 공중 공통 |
|---|---|---|
| 공격 주기 | 1,000 ms | 1,000 ms |
| 사거리 | 0.05 (밀착) | 0.05 |
| 유닛과 교전 | ○ | **× (교전 자체가 없다)** |
| 잡히는 수단 | `basic` · `splash` 타워 + 유닛 + `S-01` | **`antiair` 타워만** |

> 공중 적은 유닛에게 막히지도, 유닛을 때리지도 않는다. 그냥 **지나간다.**
> 정찰은 지상 속공보다도 빠르므로 대공이 없으면 확정 실점이다.

#### 페이즈

| 페이즈 | 조건 | 스프라이트 |
|---|---|---|
| **1페이즈** | `hp / maxHp >= 0.5` | `tf-boss-p1` (기본 패턴) |

`BOSS_PHASE2_HP_RATIO = 0.5`. 두 페이즈에 같은 HP 예산을 준다 — 플레이어 DPS가 보스전
동안 대체로 일정하므로 전환 HP 비율이 곧 화면 시간 비율이다. 부등호가 `<`(미만)라
HP 단조 감소 하에서 전환은 **한 방향으로 정확히 한 번만** 일어난다.

페이즈 판정 함수 `bossPhaseOf`는 `src/combat/boss.ts`가 소유한다 — 렌더러가 0.5를
따로 하드코딩하면 상수를 바꿔도 그림만 안 바뀐다.

#### 보스가 위협인 이유는 스탯이 아니라 **표적 우선순위 안에서의 위치**다

타워는 사거리 안에서 **x가 가장 작은(본진에 가장 가까운) 적**을 쏜다(`pickPriorityTarget`).
보스를 느리게 잡았더니 뒤에 스폰된 잡졸이 전부 보스를 추월해 **보스가 영원히 2순위**가 되고,
한 대도 안 맞고 본진까지 걸어갔다. 속도를 일반 적과 같게 두고 스폰 계획 **맨 앞**에 두면
보스는 언제나 선두 = 1순위 표적이 되어, **"보스를 먼저 지울까, 뒤따르는 무리를 막을까"**라는
실제 선택이 생긴다.

#### 마지막 웨이브의 산술

```
잡졸 14체 전부 누출 = 지상(3×4 + 3×6 + 3×8) + 공중(2×4 + 3×8) = 54 + 32 = 86  < 100  (죽지 않는다)
보스까지 누출        = 86 + 18 = 104 > 100  (죽는다)
```

**보스 하나만으로는 안 죽지만, 보스가 마지막 한 방이 된다.**

이 값은 **상한**이다. `S-03`을 쓸 때마다 −150이고, 웨이브를 놓쳐 적을 못 잡으면 드롭분도 준다.

### 8-1. 매매 수식

파라미터 (`src/position/constants.ts` `DEFAULT_POSITION_PARAMS`):

| 상수 | 값 | 의미 |
|---|---|---|
| `payoutBase` | **0.9** | 배당 계수 B |
| `zMax` | **3.0** | z 클램프 상한 |
| `feeRate` | **0.01** | 거래 수수료 1% |
| `liquidationLine` | **1.0** | 강제 청산선 (원금 100% 손실) |
| `minHoldMs` | **2,000** | 최소 보유 시간 2초 |
| `maxPositions` | **24** | 스테이지당 진입 횟수 상한 |
| `LIQ_WARN_RATIO` | **0.8** | 청산선의 80%에서 UI 적색 경고 |
| `sigma` | `ChartSet.sigma30` | 30분 구간 수익률 표준편차(%) |

#### 진입 (`openPosition`)

```
stake = floor(AUM × stakeRatio)        // 10% / 25% / 50% / 100%
fee   = round(stake × 0.01)            // 선차감분, 지갑에서는 stake만 빠진다
AUM  -= stake
```

거부 사유: `ALREADY_OPEN`(동시 보유 1개) · `MAX_POSITIONS`(24) · `INSUFFICIENT_AUM` · `INVALID_STAKE`

#### 평가 (`evaluatePosition`) — 매 프레임

```
sign     = (long ? +1 : −1)
deltaPct = sign × (현재가 − 평균단가) / 평균단가 × 100
z        = deltaPct / sigma30
r        = 0.9 × clamp(z, −3, +3)
pnl      = max( round(stake × r − fee), −stake )

강제청산  ⇔  r ≤ −1.0
경고표시  ⇔  r ≤ −0.8
```

`sigma`나 `openPrice`가 0인 비정상 입력에서는 `deltaPct`/`z`를 0으로 방어한다 —
NaN이 새면 청산선 비교가 항상 false가 되어 **강제 청산이 무력화**된다.

#### 추가 매수 (`addToPosition`) — 물타기 / 불타기

```
addStake  = floor(AUM × ratio)
addFee    = round(addStake × 0.01)
newStake  = stake + addStake
newFee    = fee + addFee                        (수수료 누적)
shares    = stake / openPrice                   (최초분 주식 수)
addShares = addStake / price                    (추가분 주식 수)
newPrice  = newStake / (shares + addShares)     ★ 주식 수 가중 평균
AUM      -= addStake
```

**왜 "투입금액 가중"이 아니라 "주식 수 가중"인가**: 두 로트를 따로 들고 있을 때의 손익 합과
합친 포지션의 손익이 **모든 가격 P에서 항등**이 되는 평균은 오직 주식 수 가중뿐이다.
투입금액 가중은 이 항등식을 깨서 없는 손익을 만들어낸다.

`seq` · `openAtMs` · `liqLine`은 최초 진입 값을 **유지한다.** 특히 `openAtMs`를 갱신하면
추가 매수마다 최소 보유 시간이 리셋되어 청산 무한 지연 우회로가 생긴다.

**★ 청산선이 밀리는 것은 설계 목적이다 ★** 손실 중 추가 매수 → 평균 단가가 현재가 쪽으로
당겨짐 → `|z|` 감소 → `r`이 청산선에서 멀어짐. **"물타기로 버티면 여유가 늘어나고,
그 대가로 타워를 세울 돈이 준다."**

#### 청산 (`closePosition`)

```
proceeds   = max(stake + pnl, 0)
goldGained = floor(proceeds × GOLD_CONVERSION)   // 0.50

gold += goldGained
aum  += 0                                        ← 복귀 없음
```

- 강제 청산(`pnl === −stake`)이면 대금이 0 → `goldGained`도 정확히 0.
- 골드는 정수 재화이므로 **내림**(올림/반올림은 전환율을 미세하게 유리하게 만든다).
- `reason`이 `liquidated`/`stage_end`(서버 강제)이면 `minHoldMs` 검사를 건너뛴다.

### 8-2. ★ 왜 "이익만 골드"가 아닌가 — 세탁 경로 차단 이력

| 버전 | 규칙 | 문제 |
|---|---|---|
| v1.1 | 성공 시에만 골드 전환 | — |
| v1.2 | **이익만 골드 · 원금 70%는 AUM 복귀**(`REFUND_RATIO`) | ① 개념이 어긋남 — 청산은 자본 회수가 아니다 ② **원금이 재순환**해 세션 총 투입이 시작 AUM의 5~6배로 불어나고, 그 배수가 밸런스의 숨은 변수가 됨 |
| **v1.3~현재** | **원금 + 손익이 통째로 × 0.50 골드 전환 · AUM 복귀 없음** | 세션 총 투입 S가 `시작 AUM + 드롭`으로 못 박힘 |

`GOLD_CONVERSION = 0.50`은 임의값이 아니라 R1의 두 앵커에서 역산한 값이다:

```
앵커 ① R1 시작 AUM 2,000  (PRD §9.2 AUM_BY_DESK_LV Lv1, v1.0부터 불변)
앵커 ② AUM_DROP_PER_WAVE 150  (= S-03 비용, "실드 1회 = 웨이브 1개분 드롭" 환율 유지)
→ S = 2,000 + 150 × 13 = 3,950
→ 구 목표 ρ = 0.20에서 필요지출 2,700에 닿으려면
   GC = (2700 − 315) / (1.20 × 3950) = 0.5032 → 0.50 (오차 0.6%)
```

**⚠️ 그러나 세탁은 현재 게이트를 통과한다.** z≈0 왕복(무판단 전환)의 R1 골드 상한은
`315 + 3,950 × 0.99 × 0.50 ≈ 2,267 G`인데 필요지출은 2,130 G다 — **137 G 초과.**
목표 수익률이 ρ = 0으로 내려간 이상 "원금을 한 푼도 안 태우는" 플레이가 막힐 방법이 구조적으로 없다.
남은 방어선은 세 가지다:

1. **보상의 단조성은 유지된다** — 같은 AUM을 z = +0.5로 굴리면 세탁보다 450 G를 더 번다.
   세탁의 여유분(137 G)의 **3.3배**이며, 137 G로는 기본 포탑 1기(120 G)를 겨우 산다.
2. **`aumGate`가 닫혀 있다** — 이익 청산 0회이므로 잔여 AUM 크레딧이 0.
3. 세탁을 다시 막으려면 ρ 게이트가 아니라 **진입/청산 횟수·시간 비용** 쪽에 걸어야 한다
   (`src/position/economy-exploit.test.ts`가 이 상태를 회귀 방어선으로 고정한다).

또한 **AUM은 의도적으로 나쁜 저장 수단**이다: 쥐고 있으면 정산에서 15%(`AUM_SETTLEMENT_RATIO`)밖에
못 건지고, 굴리면 전환에서 절반이 깎인다. 어느 쪽이든 "쌓아두기"가 답이 되지 않는다.

### 8-3. 골드 총액 공식

```
총골드 = noTradeGold + S × (1 + ρ) × GOLD_CONVERSION

  noTradeGold = 시작 골드(120) + 기본 수입 총액
  S           = 시작 AUM + 150 × 13
  ρ           = 세션 매매 수익률 (청산 pnl 합 / 총 투입액)
```

원금까지 골드가 되므로 **ρ는 1 위에 얹히는 항**이다. 그래서 ρ 5%p 변화가 총골드를
약 5%만 움직인다 — 원금-이익 분리 시절보다 게이트 대역이 구조적으로 좁다.

### 8-4. 필요지출과 게이트

```
requiredSpend = noTradeGold + S × DEPLOYMENT_ALLOWANCE × GOLD_CONVERSION
                                   └ 0.92 (S 소진율 여유)
ρ*(산술적 실패선) = (requiredSpend − noTradeGold) / (S × GOLD_CONVERSION) − 1  ≈ −8%
```

`DEPLOYMENT_ALLOWANCE = 0.92`인 이유: 봇 실측 소진율이 전액 투입 93~98% / 절반 투입 87~96%인데,
**절반 투입 쪽이 더 잘 클리어한다.** 여유를 전액 투입 소진율(0.95)로 잡으면 "몰빵하지 않은 대가"를
게이트가 벌준다 — 리스크 관리를 실력 축으로 삼겠다는 결정과 정면으로 어긋난다.
두 프리셋을 모두 덮는 0.92를 쓴다.

- `targetReturnRate` (설계 의도) = **전 지역 0** — "벌어라"가 아니라 **"받은 AUM을 태우지 말고 전부 골드로 옮겨라"**
- `gateReturnRate` (산술적 실패선) = **−8.10% / −8.00% / −7.91%**

### 8-5. 정산 (`src/app/settlement.ts`)

```
잔여골드율 = 잔여 골드 / 총 획득 골드   (총 획득 = 시작 골드 + 기본 수입 + 청산 대금)
적중률     = pnl > 0 청산 수 / 총 청산 수
본진HP율   = 잔여 본진 HP / 최대 본진 HP
```

**점수** (최대 7점):

| 항목 | +2 | +1 |
|---|---|---|
| 잔여골드율 | ≥ 0.20 | ≥ 0.10 |
| 적중률 | ≥ 0.65 | ≥ 0.55 |
| 본진 HP율 | ≥ 0.90 | ≥ 0.70 |
| 적 본진 파괴 | — | +1 (**항상 false**, §13) |

**등급과 배수**:

| 점수 | 등급 | 등급 배수 |
|---|---|---|
| ≥ 6 | **S** | ×1.6 |
| ≥ 4 | **A** | ×1.3 |
| ≥ 2 | **B** | ×1.1 |
| 그 외 | **C** | ×1.0 |

**자본금**:

```
aumGate     = (이익 청산 수 >= 4) ? 1 : 0
aumCredit   = floor(max(잔여 AUM, 0) × 0.15 × aumGate)
baseCapital = max(잔여 골드, 0) + aumCredit

보너스 배수 = 1
            + (본진 HP 만피면 +0.20)
            + (적중률 ≥ 0.70 → +0.30 / ≥ 0.60 → +0.15)   ← 상위 구간만, 중복 아님

자본금 = cleared ? floor(baseCapital × 보너스 배수 × 등급 배수) : 0
```

`aumGate`가 "총 진입 횟수 ≥ 4"가 아니라 **"이익 청산 횟수 ≥ 4"**인 이유:
진입은 아무 판단 없이도 채울 수 있어서, 예전 규칙은 **"4번만 왕복하면 됩니다"라는
익스플로잇 안내문**이 돼 있었다. 이익 청산은 z≈0 왕복으로 절대 충족되지 않는다.

가정 위에 서 있었고, 실측이 그것을 부정했다 — **×2.68의 R3는 모든 예산·모든 로드아웃에서

그래서 v1.5에서 계수를 **×1.20 / ×1.30**으로 실측 스윕에서 재산출했고, 램프의 정의를 둘로 바꿨다:

1. **총 적 HP 단조 증가** — 20,155 < 24,186 < 26,226 (`stages.test.ts`가 고정)
2. **실측 클리어율 단조 감소** — 위 표

그 결과 `combatLoadPerGold`는 오히려 **감소**한다(8.80 → 7.35 → 5.59). 이는 버그가 아니라
지표가 난이도 정의에서 물러난 결과이며, 테스트가 회귀 방어선으로 이 감소를 고정한다.

> **⚠️ `src/combat/stages.ts`의 인라인 주석은 이 개정을 반영하지 못하고 v1.4 수치(×1.62 / ×2.68,
> 총 적 HP 31,198 / 51,600, 골드당 8.41 / 9.48 / 11.00)를 그대로 말한다.** 실제 코드는 ×1.20 / ×1.30이다.
> 자세한 것은 §13.

### 10-1. 블라인드 규칙 (FR-4)

`ChartSet`(`src/market/types.ts`)에는 **종목명·날짜 필드 자체를 두지 않는다.**

|---|---|
| 불투명 ID(`id`) | 종목명 · 티커 · 날짜 |
| 시가 대비 등락률 (`+0.00%`) | 절대 가격 |
| 거래량 배수 (`2.4×`) | 절대 거래량 |
| 태그: `BLIND` / 아시아 / 금융 / 대형주 | 그 외 식별 정보 |

화면 시계는 `09:00`부터 봉 인덱스 단위로 흐른다(`formatSessionClock`, 마지막 봉 = 15:29).

| **WX-03** | `range_fog` | 무채색 안개 띠 2겹 | `σ30 ≤ 0.6%` **그리고** `|등락률| ≤ 0.5%` |
| **WX-04** | `blackout` | 정전 + 굵은 스캔라인 2줄 | 거래 정지(서킷브레이커) |
| — | `clear` | 오버레이 없음 | 그 외 |

**우선순위** (위가 강함): ① `blackout` ② 활성 시장 이벤트 ③ `range_fog` ④ `|z|` 임계 ⑤ `clear`

> ★ ③이 ④보다 위인 이유: σ 하한 때문에 무변동 구간에서 z가 쉽게 커진다.
> 안개를 먼저 걸러내지 않으면 **횡보장에 폭우가 내린다.**

**강도(intensity)는 0~1 연속값이며 절대 단계형으로 양자화하지 않는다.**
급락이 심할수록 폭우가 연속적으로 굵어져야 플레이어가 화면만 보고 시장의 정도를 읽는다.

| 상수 | 값 | 의미 |
|---|---|---|
| `Z_SIGMA_FLOOR_PCT` | 0.05 | z 분모 하한(%). 손익용 σ 하한(0.01)보다 보수적 |
| `DIRECTIONAL_MIN_Z` | 1 | 방향성 날씨 시작 임계 |
| `DIRECTIONAL_FULL_Z` | 4 | 강도 1 포화 |
| `FOG_MAX_SIGMA_PCT` | 0.6 | 안개 판정 σ 상한 |
| `FOG_FULL_SIGMA_PCT` | 0.1 | 안개 강도 1 도달 σ |
| `FOG_MAX_ABS_CHANGE_PCT` | 0.5 | 안개 허용 최대 등락률 |
| `EVENT_WINDOW_MS` | 30,000 | 이벤트 1건이 날씨를 지배하는 시간 |
| `EVENT_INTENSITY_FLOOR` | 0.6 | 이벤트 활성 중 보장 최소 강도 |
| `BLACKOUT_MAX_FRAMES` | 3 | 정전 지속 상한(시트: "3프레임 이내로 짧게") |

정전은 시간축 상한을 `src/weather/resolve.ts`가 따로 건다. 카운터를 "정전이 보이는 동안"만 세면
정지가 이어지는 내내 3프레임마다 재점멸하므로, **정지 구간 전체**를 세고 정지가 풀릴 때만 0으로 되돌린다.

### 10-5. 발판(GROUND) 3단계 — 전황 표시

`src/ground/` · 임계값은 `src/ground/constants.ts`

| 상태 | 조건 | 표시 |
|---|---|---|
| `intact` | 최대 전진율 < 0.5 | 정상 |
| `cracked` | 최대 전진율 ≥ 0.5 | 균열 |
| `collapsed` | 균열 + **후반 웨이브** (`wave ≥ ceil(13 × 0.7)` = **10웨이브부터**) | 함몰 + 청색 잔광 |

**평균이 아니라 최대(가장 전진한 적) 기준**인 이유: 평균은 새 적이 x≈1에 스폰될 때마다
내려가서, 적 하나가 사옥 코앞에 붙어 있어도 발판이 '정상'으로 되돌아간다 —
전황 표시가 위협을 **가리는** 셈이라 정보로서 실패한다.

함몰이 균열 **위에** 얹히는 이유: "정상 = 웨이브 시작 상태"라는 시트 규칙을 지키기 위해서다.
후반이라는 사실만으로 곧장 함몰로 보내면 후반 웨이브 시작 순간부터 이미 무너져 있게 된다.

### 10-6. 슬롯 데칼 3상태

| 상태 | 조건 | 표시 |
|---|---|---|
| `inactive` | 타워를 고르지 않음 (`buildCost === null`) | 점선 사각 |
| `placeable` | 빈 슬롯 + 골드 충분 | 적색 실선 + 코너 브래킷 |
| `blocked` | 이미 찼거나 **골드 부족** | 회색 사선 해칭 |

골드 부족이 `blocked`로 나오는 것이 이 데칼의 핵심이다 — "매매를 해야 방어가 선다"를
화면이 먼저 말해 줘야 한다.

|---|---|---|

| 동시 재생 상한 | `MAX_CONCURRENT_VOICES = 6` | 한 순간에 의미 있는 최대 조합(웨이브+피격+처치+발사+스킬+청산) 크기. 넘치면 **`priority`가 낮은 것이 밀려난다** — 타워 발사(1)가 보스 등장(9)을 가리는 일이 구조적으로 불가능하다 |

**★ 자동재생 정책** — 브라우저는 첫 사용자 제스처 전까지 `AudioContext`를 `suspended`로 둔다.
그래서 게임 진입 경로 넷(자유 플레이 · 일일 챌린지 · 시드 입력 · 지역 카드)과 사운드 컨트롤
조작에서 `audio.resume()`을 부른다. 마운트 시점에 미리 부르면 브라우저가 거부한다.

**설정 UI** — 컨트롤 바 오른쪽에 음소거 토글 + 마스터 볼륨 슬라이더.
`localStorage` 키 `ticker-front.audio`(버전 필드 포함, `progress.ts`와 같은 패턴).
기본값은 **음소거 아님 / 볼륨 0.45**(소리별 상대 볼륨과 곱해져 실출력 최대 0.21).

⚠️ **음소거는 "볼륨 0 저장"이 아니다.** 끄기 전 볼륨을 기억해야 다시 켤 때 원래 크기로
돌아온다. 화면도 `0%`와 `음소거`를 다르게 쓴다 — 두 사실은 별개다.

⚠️ **소리는 보조 채널이다.** `AudioContext`가 없는 환경(node·jsdom·구형 브라우저·
저장소 차단)에서 **전부 조용히 무음으로 떨어진다.** 소리 없이도 게임이 완전히 플레이
가능해야 한다 — 지금 그렇다. 깨지 마라.

### 11-8. 접근성 그 외

- `prefers-reduced-motion` 존중 — 모션은 멈추되 **시장 상태 정보는 그대로 전달**한다.
- 골드 카운트업은 `role="status" aria-live="polite"`로 스크린리더에 알린다.
- 지역 선택·결과 화면은 `role="dialog" aria-modal="true"` + 첫 요소 자동 포커스.
- HUD 아이콘은 `aria-hidden` — 라벨과 중복 낭독되지 않게 한다.
- `Space` 가로채기는 텍스트 필드와 **키보드 포커스된 버튼**을 예외로 둔다(`:focus-visible`).
- 44px 터치 타겟을 지키기 위해 슬롯 간격 `0.035`(레인폭 778px 기준 54.5px)를 최소치로 잡았다.

### 12-4. 검증 도구 2종

두 도구는 **서로 다른 질문**에 답한다.

| 도구 | 질문 | 실행 |
|---|---|---|
| **`tools/bot-sim`** | "필요지출만큼 **벌 수 있는가**" (경제 게이트) | `npm run bot-sim` |
| **`tools/combat-sim`** | "그 돈으로 산 방어가 **막는가**" (전투 게이트) | `npm run combat-sim` |

**bot-sim** — 7개 전략(무작위 / 추세추종 / 거래량반응 × 손절규율 유무 + 종료보유) × 3지역 ×
2 차트 공급원(`synth` / `martingale`) × 기본 200판. 시드 고정이라 같은 명령이 항상 같은 표를 낸다.
`martingale` 공급원은 실제 장중 1분봉의 통계적 성질(무추세 마팅게일 + 변동성 군집 + U자 거래량)을
재현한다 — 합성기의 결정론적 추세 위에서 판정하면 "게임의 성질"이 아니라 "합성기의 성질"을 재는 셈이 되기 때문이다.

**combat-sim** — 19개 로드아웃 × 3지역 × 예산비 3단(50/75/100%). 로드아웃 목록은
"어떤 조합이 이기는가"가 아니라 **선택이 결과를 가르는가**를 보도록 축을 하나씩 분리한다:
① 타워 종류 ② 공중 대비(대공 0/1/2기) ③ 타워 vs 유닛 ④ 유닛 종류 ⑤ 업그레이드(폭 vs 깊이).
어떤 축을 흔들어도 결과가 같으면 그 축은 **죽은 결정**이다.

이 도구들이 실제로 잡아낸 것:
- 유닛이 **마이너스 가치**였다는 사실 (예산 1,560 G 추가 시 잔여 HP 40 → 16) → `UNIT_HOLD_LINE` 도입
- 보스가 **한 대도 안 맞고** 본진까지 걸어간다는 사실 → `BOSS_SPEED` 원복
- "포탑만 만들어두면 이김" → 타워 피해량 약 1/2 하향 + Lv2 배수 상향
- R3 `×2.68` 계수의 클리어율 **0%** → `×1.30`으로 재산출

### 13-2. 데이터·밸런스

| 항목 | 내용 |
|---|---|
| **실데이터 미연결** | 차트는 전부 `generateChartSet(seed)` 합성기 산출이다. 실제 과거 거래일 데이터가 붙지 않았으므로 **"진짜 그 날"이 존재하지 않는다** — 공개 연출이 미구현인 것과 같은 뿌리다 |
| **★ 합성 차트에서는 매매 난이도가 사실상 없다** | 봇 실측: `synth` 공급원에서 최선 전략 ρ가 **+146%**, 클리어율 **98~100%**다. 합성기가 아키타입별 결정론적 추세(급등 하루 +18% 등)를 깔아서 "추세를 따라가면 이긴다"가 성립하기 때문이다. `martingale` 공급원(실제 1분봉 성질)에서는 최선 ρ가 +2~3%로 떨어진다. **즉 현재 플레이어가 실제로 겪는 매매는 봇 시뮬레이터가 밸런스를 잡은 그 차트가 아니다** |
| **세탁이 통과한다** | z≈0 무판단 왕복의 R1 골드 상한 2,267 G > 필요지출 2,130 G. 목표 ρ가 0인 이상 구조적으로 막을 방법이 없다. 남은 억제책은 보상 단조성(숙련이 450 G 더 번다)과 `aumGate`(이익 청산 4회)뿐 |
| **`S-03` 저평가** | 실효 골드 비용 75 G로 `S-01`(200 G)의 절반 이하다. 300 AUM으로 올리면 균형이 회복되지만 정산식·게이트 개정 범위 밖이라 보류. ⚠️ `constants.ts` `SKILL_SPECS` 주석은 아직 **90 G**(ρ=0.20 시절 값)로 적혀 있다 — 주석만 고치면 되는 잔여 부채 |
| ~~날씨가 뜨지 않음~~ | ✅ **해소됨** (`655788c`). `marketZ`의 분모가 측정 윈도와 어긋나 변동성 큰 차트에서 방향성 날씨가 0회였다(§19-13) |
| **클리어율이 낮다** | 예산 100%에서도 19개 로드아웃 중 클리어는 R1 6 / R2 3 / R3 3개뿐이다(**0.316 / 0.158 / 0.158**, `b70b6c4` 이후). "13웨이브를 적당히 잘하면 깰 수 있다"는 목표 대비 **정답 조합이 좁다** — 사실상 `기본4+대공2 Lv2` 계열과 `타워6+사환` 혼합만 통과한다. ⚠️ 기준선의 R1 클리어 7종 중 **3종은 잔여 HP가 4**였다(razor-thin) — 이 지표는 후반 부하가 5%만 움직여도 통째로 흔들린다 |

### ⚠️ 새로 생긴 함정 3건

1. **동적으로 다시 그리는 화면의 버튼에 리스너를 직접 걸지 마라.**
   도감 본문·세계지도 목록·회사 부서 목록은 전부 `innerHTML` 교체다. 버튼별 리스너는
   첫 렌더에서만 살아 있고 그 뒤로는 죽은 화면이 된다. **위임으로 받아라** —
   `stage.ts`의 `codexBody`/`worldList`/`worldBrief`/`companyBody` 리스너가 그 패턴이다.

2. **선택 상태를 DOM에서 읽지 마라.** 본문이 교체되면 class 에 실어 둔 상태가 함께
   사라진다. `codexFilter`·`worldSelection`이 셸의 지역 변수로 나와 있는 이유다.

3. **`GameProgress`에 필드를 더하면 테스트 픽스처가 전부 깨진다.** 타입이 `readonly`
   전수 필드라 객체 리터럴이 바로 컴파일 오류가 된다 — 이건 기능이다(빠뜨림을 tsc가 잡는다).
   `emptyProgress()`를 펼쳐 쓰는 편이 낫다.

### 15-5. 실데이터 연결 + 서버 `[P0/P1 — 범위 판단 필요]`

**왜**
공개 연출 2·3단계(종목명·날짜·뉴스)가 실데이터 없이는 불가능하다. 즉 **H2 검증이 원천적으로 막힌다.**
또 블라인드 규칙(FR-4)이 클라이언트 단독 실행에서는 강제되지 않는다 — 개발자 도구로 `ChartSet`을 읽을 수 있다.

**⚠️⚠️ 가장 큰 함정 — 실데이터로 가면 밸런스가 통째로 무너진다 ⚠️⚠️**

현재 합성 차트(`src/market/synth.ts`)는 아키타입별 **결정론적 추세**를 깐다(급등 하루 +18% 등).
그 결과 surge/plunge 차트의 하루 등락이 `sigma30` 대비 **±31σ**에 달한다.

| 차트 공급원 | 최선 전략 ρ | 클리어율 |
|---|---|---|
| `synth` (현재 게임이 쓰는 것) | **+146%** | 98~100% |
| `martingale` (실제 1분봉 성질) | **+2~3%** | 49~52% |

즉 **현재 플레이어가 겪는 매매 난이도는 사실상 없다.** 실데이터로 바꾸면 마팅게일 경로가 되고,
그 경로에서는 `E[r] = 0`이므로 어떤 정지 규칙을 써도 `E[ρ] ≤ −feeRate`가 **정리로 성립**한다.
상한이 ρ ≈ 0(±3%p)으로 내려간다.

**따라서 실데이터 전환 시 반드시 함께 해야 할 일**:
1. `npm run bot-sim --regimes=martingale`로 게이트 판별력 재확인 (현재 23~26%p 격차 유지되는지)
2. `requiredSpend`가 여전히 ρ=0에서 닿는지 확인 — **닿지 않으면 전투 쪽을 낮춰라**(15-4 검증과 같은 원칙)
3. 세탁 상한(2,267 G)과 필요지출(2,130 G)의 관계 재계산

**어디를 건드리나**
- `src/market/synth.ts` → 데이터 소스 교체. **`ChartSet` 인터페이스는 그대로 두어라** —
  `tools/bot-sim/charts.ts`가 이미 `src/`를 건드리지 않고 다른 공급원을 만드는 데 성공했다. 같은 방식.
- 서버: `openTrade` / `closeTrade` / `syncLiquidation`이 서버 왕복으로 바뀌어야 한다.
  세 함수만 바꾸면 되도록 `session.ts`가 이미 얇게 설계돼 있다.

### 16-6. 법무팀(청산선 완화)은 **실력이 늘수록 가치가 0이 된다** (2026-08-05 실측)

§15-4가 *"`bot-sim`으로 법무팀 Lv3이 Lv1보다 실제로 유리한지 반드시 확인해라. 불리하게

`bot-sim`에 청산선 옵션이 없어 `engine.ts`의 `DEFAULT_POSITION_PARAMS` 스프레드에
`liquidationLine`을 임시 주입해 측정했다 (R1 · martingale · 120판, 측정 후 원복).

**손절 규율이 없는 전략** — 법무팀이 실제로 이득이다:

| 청산선 | 거래/판 | ρ | 총골드 | 강제청산율 |
|---|---|---|---|---|
| 1.00 (Lv1) | 8.7 | −2.1% | 2,118 | 28.4% |
| 1.15 (Lv2) | 8.6 | −0.8% | 2,142 | 23.1% |
| 1.30 (Lv3) | 8.4 | **+0.8%** | **2,171** | **17.5%** |

거래량반응도 같은 방향(+1.8% → +5.3%, 총골드 2,194 → 2,258).

⚠️ §15-4가 우려한 **"회전율 저하로 손해"는 나타나지 않았다.** 거래/판은 −3.4%,
S 소진율은 93~94%로 사실상 불변인데 ρ는 +2.9~3.5%p 오른다. 청산 방어 이득이 회전율
손실보다 크다. **"돈 주고 사면 손해인 부서"는 아니다.**

**★ 그런데 손절 규율을 쓰는 전략에서는 효과가 정확히 0이다 ★**

| 손절 규율 있음 | 1.00 | 1.15 | 1.30 |
|---|---|---|---|
| ρ | +2.2% | +2.2% | +2.2% |
| 강제청산율 | 0.1% | 0.0% | 0.0% |

손절을 하면 강제청산에 애초에 걸리지 않으므로, 청산선을 아무리 완화해도 **바뀌는 것이
하나도 없다.** 즉 법무팀은 **"손절을 안 하는 플레이어에게만" 값어치가 있다.**

이것은 §15-4가 예상한 실패 모드("손해")와 다른 형태다 — **실력이 늘수록 가치가 0으로
수렴한다.** v1.4가 실력 축을 **리스크 관리**로 선언한 것과 정면으로 어긋난다:
게임이 가르치려는 바로 그 습관(손절)을 익히면 이 부서가 죽는다.

**후보**:
1. 법무팀 효과를 청산선이 아닌 다른 것으로 바꾼다 (예: 강제청산 시 진입 횟수 회수)
2. 그대로 두되 **"초보 보험"**으로 명시한다 — 화면이 그 성격을 말해야 한다
3. 청산선 완화 + 소액의 상시 이득을 얹어 숙련자에게도 0이 아니게 한다

### 17-2. ★ 경계 규칙 (이걸 어기면 테스트가 붙지 않는다)

| 규칙 | 의미 |
|---|---|
| **판정 모듈은 Canvas·DOM·타이머·전역 상태를 모른다** | `combat`·`position`·`weather`·`ground`는 `document`·`window`·`performance`·`Date.now()`를 절대 참조하지 않는다. 그래서 헤드리스로 전부 검증된다 |
| **렌더 모듈은 시장 지표를 모른다** | `battle`은 `MarketConditions`를 받지 않는다. `WeatherView`(판정 결과 + 연출 파라미터)만 받는다 |
| **시계는 주입한다** | `Replay.tick(nowMs)` · `step(state, dtMs, params)`. `performance.now()`를 읽는 곳은 `src/app/stage.ts`의 프레임 루프 **한 곳뿐** |
| **의존 방향은 단방향** | `weather`/`ground`는 `combat`을 import하지 않는다 — 필요한 필드만 구조적으로 좁혀 받는다(`AdvancingEnemy`, `WeatherViewport`). 이 방향이면 순환이 생기지 않는다 |
| **불변 상태 전이** | 입력 배열·객체를 변형하지 않고 항상 새 것을 반환한다 |
| **스탯은 개체에 실린다** | `kind`로 전역 상수 테이블을 조회하지 마라. 상수는 **생성 시점의 기본값 출처**일 뿐이다 |
| **프레임당 할당 0** | 사망 없는 틱은 같은 빈 배열 참조를 돌려준다. 날씨·사망 연출 버퍼는 앱 수명 동안 하나 |
| **단일 출처** | 이름·역할 = `identity.ts` / 밸런스 = `constants.ts`·`stages.ts` / 색 = `palette.ts` / 스킬 문구 수치 = 상수 파생 |

### 17-3. 계약 파일 (양쪽이 이것만 보고 독립 구현할 수 있어야 한다)

| 파일 | 잇는 것 |
|---|---|
| `src/combat/types.ts` | 전투 시뮬레이션 ↔ 전장 렌더러 |
| `src/market/types.ts` | 리플레이 엔진 ↔ 차트 렌더러 |
| `src/weather/types.ts` | 날씨 판정 ↔ 날씨 렌더러 |
| `src/ground/types.ts` | 발판 판정 ↔ 발판 렌더러 |

**이 파일들에 구현 세부를 넣지 마라.**

### 17-4. 좌표계

전장은 좌우 1레인이다. `x`는 **0(아군 사옥) ~ 1(적 본진)**로 정규화된 진행도다.
픽셀은 렌더러가 정한다 — **시뮬레이션은 화면 크기를 몰라야 한다**(`battle/layout.ts` `progressToX`).

- 적: `x = 1`에서 스폰 → 0으로 **감소**
- 유닛: `x = 0`에서 소환 → 1로 **증가** (단 `UNIT_HOLD_LINE = 0.45`에서 멈춘다)
- 타워: `towerX(slot) = slot × 0.035`

### 18-2. 밸런스 시뮬레이터 2종

**두 도구는 서로 다른 질문에 답한다. 밸런스를 건드렸다면 해당하는 쪽을 반드시 돌려라.**

```bash

```

**bot-sim 옵션**

```bash
npm run bot-sim -- --runs=200 --seed=20260731 --stages=R1,R2 \
                   --regimes=martingale --stake=0.5 --strategies=trend
```

- `--regimes=martingale` — **실제 1분봉 성질**. 밸런스 판단은 이쪽으로 해라
- `--regimes=synth` — 현재 게임이 실제로 쓰는 합성기(난이도가 사실상 없음)
- 시드 고정이라 같은 명령이 항상 같은 표를 낸다
- 봐야 할 것: **"설계 축 — 게이트가 전략을 판별하는가"** 표의 격차(%p). 현재 23~26%p

**combat-sim 옵션**

```bash
npm run combat-sim -- --stages=R1 --ratios=1 --loadouts=t-mix-up
```

- 19개 로드아웃 × 3지역 × 예산비 3단(50/75/100%)
- 봐야 할 것: **요약 표의 클리어율이 R1 > R2 > R3로 단조 감소하는가**
- 로드아웃은 **축을 분리**한다(타워 종류 / 대공 기수 / 타워vs유닛 / 유닛 종류 / 폭vs깊이).
  어떤 축을 흔들어도 결과가 같으면 그 축은 **죽은 결정**이다

**타워 종류 축 전용 도구**

```bash
npx tsx tools/combat-sim/tower-axis.ts              # 전 지역
npx tsx tools/combat-sim/tower-axis.ts --stages=R2  # 지역 한정
```

`bin.ts`의 19개 로드아웃 표는 종류 비교가 **투자액이 달라 공정하지 않다**(`기본4+대공2`는
Lv2 1,800 G인데 `광역4+대공2`는 Lv1 880 G다). 이 도구는 **같은 슬롯 수·같은 대공 기수·같은
업그레이드 단계**로 지상 4기의 종류만 바꾸고, 웨이브별 실점을 구간으로 접어 보여준다.

- ⚠️ **`LOADOUTS`(19종)에 로드아웃을 추가하지 마라.** 그 개수가 요약표 클리어율의 분모이고
  밸런스 이력이 전부 "19개 중 몇 개"로 기록돼 있다 — 늘리는 순간 과거 수치와 비교가 끊긴다.
  새 비교군이 필요하면 이 도구처럼 **분모를 건드리지 않는 별도 파일**로 뽑아라.
- 봐야 할 것: **한 종류로 도배한 방어가 어느 구간에서 새는가.** 도배가 항상 최적이면 종류
  축은 죽은 결정이다. 현재는 `단일2+광역2` 혼합이 양쪽 도배를 이긴다(§5).

### 19-1. 디자인 스프라이트를 글로 된 묘사만 보고 재현하지 마라

**원본이 있다.**

| 파일 | 내용 |
|---|---|
| `docs/design-reference/ticker-front-sprites.js` (66 KB) | **원본 드로잉 코드** — `sheets()` 전체 |

| `docs/design-reference/extract.mjs` | 원본 → grids.json 추출 스크립트 |

좌표를 그대로 옮기고 **문자 단위로 대조해라**. `src/sprites/grids.test.ts`가 이 대조를 자동화한다.
묘사를 보고 "비슷하게" 그리면 원본과 다른 그림이 나오고, 그 순간 아트 발주서와 코드의 1:1 대응이 깨진다.

### 19-2. 스트립 시트를 화면에 직접 쓰면 색약 모드에서 색이 튄다

`strip` / `canSpin` / `towerFire` 같은 **스트립 생성기는 팔레트 문자를 HEX로 굽는다.**
그래서 스트립 시트를 그대로 화면에 blit하면 **색약 모드에서 그 순간만 원래 색으로 튄다.**

**규칙**: 화면에는 **문자 그리드**를 쓰고, 스트립은 **참조·검수용**으로만 써라.
(`stripFrameGrid` / `stripFrameRect`가 스트립에서 프레임 하나를 되꺼내는 API다.)

### 19-3. 비교 시트를 blit하지 마라

`SCREEN_ONLY_SPRITE_KEYS`에 등록된 5키는 게임 오버레이가 아니다:

| 키 | 정체 |
|---|---|
| `tf-fx-screen` | **3패널 비교 시트** |
| `tf-sky-scrim` | before/after 비교 |
| `tf-sky-wide` | 구도 검증 시트 (**보스까지 박혀 있다**) |
| `tf-title` | 타이틀 화면 목업 |
| `tf-reveal` | 공개 화면 목업 |

추가로 `tf-ally-parts`는 **부품 참조 시트**라 게임 엔티티가 아니다.

**판별법**: **세로로 균일한 열(구분선) 개수를 세라.** `tf-sky-scrim`은 2개(x = 60, 61)로 패널을
가르는데, `tf-title`·`tf-reveal`은 0개다. 구분선이 있으면 비교 시트다.

### 19-4. 이중 출처를 만들지 마라 — **실제로 두 번 당했다**

| 사고 | 결과 |
|---|---|
| `src/app/session.ts`가 자체 `STARTING_GOLD`(200)를 들고 있었다 | `combat/constants.ts`의 밸런스를 120으로 고쳐도 **런타임은 계속 200을 읽었다** |
| `src/app/stage-dom.ts`가 자체 라벨맵('인턴', '기본 포탑')을 들고 있었다 | 아트 시트가 정한 정체성('개장벨 사환', '지지선 앵커포')이 **화면에 한 번도 닿지 않았다** |

**규칙**: 값을 두 번 적지 마라. 화면은 `identity.ts` / `constants.ts` / `STAGES` / `palette.ts`에서 **읽어라**.
새 화면을 만들 때 특히 위험하다 — `region-select.ts`가 이 규율을 지킨 좋은 예다
(카드에 적힌 숫자가 전부 `STAGES`에서 온다).

### 19-5. 배선 누락은 **번들 크기**로 확인해라

코드를 다 쓰고도 **호출부가 없으면 트리셰이킹으로 통째로 빠진다.** 실제로 발생했다.
테스트는 모듈을 직접 import하므로 **전부 통과하는데 화면에는 아무것도 안 나온다.**

**확인법**: `npx vite build` 출력의 번들 크기를 작업 전후로 비교해라. 늘지 않았으면 배선이 없는 것이다.

**이 절이 지목했던 날씨 시스템은 해소됐다** (커밋 `300ad2f`). `session.stepWeather`가 판정을
`drawBattle`에 넘기면서 번들이 154.90 → 157.20 kB로 늘었고, 날씨 4종 문자열이 번들에서 검출된다.
**그 확인 방법 자체는 그대로 유효하다** — 새 기능을 붙일 때마다 번들 크기를 전후로 비교해라.

### 19-6. 테스트 통과가 화면 동작을 뜻하지 않는다

`src/battle/fake-ctx.ts`의 `FakeBattleCtx`에는 **`drawImage`가 없다.**
(`sprite-fake-ctx.ts`에만 있다.) 그래서 다수의 전장 테스트는 **폴백 경로**(도형 드로잉)만 검증하고,
**실제 브라우저는 스프라이트 경로를 탄다.**

click-path 감사도 이것을 "이 감사가 못 본 것"으로 명시했다: *"스프라이트 굽기 실패 경로
(`FakeCtx`에 `drawImage`가 없어 미검증)"*.

**규칙**: 스프라이트 경로를 건드렸다면 **반드시 브라우저에서 확인해라.**

### 19-7. DOM 배선 테스트가 오랫동안 0건이었다 (지금은 jsdom이 있다)

예전에는 `vite.config.ts`에 vitest 설정이 없어 **node 환경**으로만 돌았고, "버튼을 누르면
실제로 무슨 일이 일어나는가"가 CI에서 검증된 적이 없었다.

**지금은 jsdom이 설치돼 있다.** 다만 **전역 기본값은 여전히 node**다(1,900여 개가 node에서
통과 중이라 전역 전환은 위험). DOM이 필요한 파일만 최상단 docblock으로 옵트인해라:

```ts
// @vitest-environment jsdom
```

⚠️ jsdom에는 **canvas가 없다** — `getContext('2d')`가 `null`이라 캔버스를 타는 배선은
여전히 검증되지 않는다(§19-6). 마크업 계약은 문자열 검사로 막는다(§19-12).

click-path 감사가 찾은 결함 5건(**CRITICAL 1** · HIGH 1 · MEDIUM 3)이 전부 이 사각에 살아남았다:
무음 전체 리셋 · 배속 버튼이 판을 지움 · 실패를 성공이라 말하는 로그 · 항상 활성인 소환 버튼 ·
삼켜지는 Space.

**규칙**: **핸들러 로직을 순수 함수로 뽑아 테스트해라.**
이미 그 패턴이 있다 — `src/app/stage-flow.ts`(`decideFrame` / `resolveSpeedChange` / `shouldSkipPrep` /
`formatActionLog`) · `src/app/settlement.ts` · `src/ui/*-logic.ts`.
`stage.ts`는 그 결과를 화면에 옮기기만 하는 얇은 층으로 유지해라.

### 19-8. 전투 난이도를 **필요지출**로 만들지 마라

매매 ρ의 현실적 상한이 0(±3%p)이므로, `requiredSpend`를 올리면 **아무도 못 깬다.**
난이도는 반드시 **"같은 돈으로 산 것이 덜 막는"** 방향으로만 만들어라
(적 HP·수·속도 / 타워 피해량·쿨다운).

같은 이유로 **타워 비용을 올리는 것도 난이도 레버가 아니다.** 슬롯이 6개로 고정이라
비용을 올려도 전달되는 피해 총량은 그대로고 남는 골드만 준다.
산출을 줄이는 레버는 **피해량·쿨다운·사거리** 셋뿐이며, 사거리는 슬롯 선택의 의미를 만드는 축이라
건드리지 않는 것이 현재 결정이다.

### 19-9. `combatLoadPerGold`(HP/골드) 단조 증가 지표는 **폐기됐다**

이 지표는 **골드가 방어로 선형 변환된다**고 가정하는데, 타워 슬롯 6개 상한 때문에 실제로는 곡선이다.
"예산이 2.05배니 적 HP도 2.68배여야 공평하다"는 계산은 성립하지 않는다.

실측이 그것을 그대로 보여줬다: 이 지표에 맞춰 계수를 정한 v1.4의 R3(×2.68)는
**모든 예산 · 모든 로드아웃에서 클리어율 0%**였다.

**규칙**: **난이도는 실측 클리어율(`combat-sim`)로 판단해라.** 비율 계산으로 정하지 마라.
현재 램프의 정의는 ① 총 적 HP 단조 증가 ② 실측 클리어율 단조 감소 둘이다.

### 19-10. 순수 함수 테스트가 통과해도 **배선이 틀릴 수 있다**

`simulate.ts`의 `spawnDue`가 `EnemySpec`의 필드를 하나씩 손으로 옮겨 적는 구조인데,
거기서 **`isBoss`를 누락**해 보스가 **일반 적으로 스폰됐다.**
`waves.ts`의 `spawnPlanFor`는 `isBoss: true`를 정확히 넣고 있었고 그 테스트도 통과했다.
결과: 보스 HP 바도 페이즈 연출도 전부 죽은 채로 마지막 웨이브가 지나갔다.

**규칙**: 스펙에 필드를 추가하면 **필드를 옮겨 적는 모든 곳을 같이 고쳐라.**
`simulate.ts:147` 근처에 경고 주석이 남아 있다.

### 19-11. 실데이터로 바꾸면 밸런스가 통째로 무너진다

현재 합성 차트는 surge/plunge가 `sigma30` 대비 **±31σ**라, 사실상 동전 던지기로도 ρ+35%가 나온다.
실제 마팅게일에서는 `E[r] = 0`이므로 어떤 정지 규칙에서도 `E[ρ] ≤ −feeRate`가 **정리로 성립**하고,
상한이 ρ ≈ 0으로 내려간다.

| 공급원 | 최선 전략 ρ | 클리어율 |
|---|---|---|
| `synth` | +146% | 98~100% |
| `martingale` | +2~3% | 49~52% |

**규칙**: 밸런스 판단은 **`--regimes=martingale`으로 해라.** 자세한 것은 §15-5.

### 19-12. ★ ref 하나가 빠지면 게임이 통째로 죽는다 — 그리고 검증 3종이 전부 통과한다

`collectStageRefs`는 **하나라도 못 찾으면 `null`**을 돌려주고, 셸은 그때 화면 전체를
"스테이지를 초기화하지 못했습니다"로 대체한다.

실제 사고: 새 버튼을 추가하면서 마크업의 `data-action="${...}"`이 **빈 문자열**로 커밋됐다
(패치 스크립트를 bash 큰따옴표 안에서 돌려 셸이 `${}`를 먼저 치환했다). 그런데

| 검증 | 결과 |
|---|---|
| `npx tsc --noEmit` | 통과 — 문자열 리터럴이라 타입 오류가 아니다 |
| `npx vitest run` | 통과 — 마크업과 ref 목록을 대조하는 테스트가 없었다 |
| `npx vite build` | 통과 — 빌드는 마크업 내용을 모른다 |
| **브라우저** | **첫 화면부터 죽음** |

**규칙**: 새 `data-ref`/`data-action`을 추가하면 **`src/app/stage-dom-refs.test.ts`의 목록에도
추가해라.** 그 파일이 계약이며, 빈 속성·치환 안 된 `${...}`·`"undefined"` 누출까지 함께 막는다.

⚠️ **마크업은 템플릿 리터럴 안이다.** 주석에도 백틱을 쓰면 문자열이 끊긴다(이것도 한 번 깨졌다).

### 19-13. ★ 분자와 분모의 **윈도를 맞춰라** — 날씨가 영원히 뜨지 않던 이유

`marketZ`가 `recentChangePct`(**10봉 = 10분** 변화)를 `sigma30`(**30분** 수익률 표준편차)으로
나누고 있었다. √t 스케일링 때문에 |z|가 구조적으로 약 0.58배가 되고, 그 결과
**변동성이 큰 차트에서는 임계(1σ)를 한 번도 넘지 못했다.**

| 시드 | `sigma30` | 고치기 전 `\|z\|≥1` | 고친 뒤 |
|---|---|---|---|
| 1 (기본) | 2.834 | **0.0%** (최대 0.83) | 7.9% |
| 2 | 2.919 | **0.0%** (최대 0.68) | 3.8% |
| 3 | 2.483 | **0.0%** (최대 0.87) | 11.8% |
| 20260803 | 0.795 | 19.2% | 44.6% |

기본 시드가 1이라 **자유 플레이에서는 390봉 내내 `clear`**였다. 날씨를 배선하고도(§19-5 해소)
화면에 아무것도 안 뜬 이유가 이것이다 — 배선은 맞았고 **판정이 영원히 같은 값을 냈다.**

**규칙 셋**:
1. 임계값을 낮춰 덮지 마라. `DIRECTIONAL_MIN_Z = 1`은 "1σ면 이례적"이라는 **뜻**을 가진 값이다.
   고칠 것은 임계가 아니라 **분모의 단위**다(`RECENT_WINDOW_SIGMA_SCALE = √(10/30)`).
2. `RECENT_WINDOW_BARS`나 σ 윈도를 바꾸면 그 계수도 같이 바꿔라.
3. **테스트가 버그와 같은 가정을 공유하면 초록이어도 소용없다.** 옛 테스트는
   `z = 등락률 / sigma30`을 손으로 적고 있었다. 관계를 헬퍼 하나에 고정해라.

### 19-14. "첫 회차" 판정을 **영원히 끝나지 않는 조건**으로 만들지 마라

튜토리얼 스킵을 `clearedCount(progress) === 0`으로 막았더니, **지역을 깨기 전에는 그 값이
영원히 0**이라 버튼이 영구 비활성이었다. 게다가 지역을 깨려면 튜토리얼을 끝까지 봐야 하는
**순환**이었다.

**규칙**: "처음인가"는 **그 행동 자체를 기록해서** 판정해라(`progress.tutorialSeen`).
다른 성취(클리어 등)로 대신하면 두 사실이 어긋나는 순간 잠긴다.

### 19-15. 화면을 겹칠 때는 **프레임 루프 정지 조건**도 같이 넓혀라

공개 연출을 정산 **앞**에 끼우면서 루프 정지 조건(`resultShown`)을 그대로 뒀더니, 루프가
계속 돌며 매 프레임 `showReveal`을 재호출해 **경과 시간이 0으로 리셋**됐다. 연출이 영원히
끝나지 않고 스킵 버튼도 다음 프레임이 즉시 덮어썼다.

**규칙**: 새 전체 화면을 추가하면 `render()` 첫머리의 정지 조건에 그 플래그를 반드시 넣어라.

### 20-1. 표준 순서

```
1. 이 문서(GAME.md)를 읽는다                 ← 특히 §17 경계 규칙, §19 함정
```

**4번을 건너뛰지 마라.** "원래 깨져 있던 것"과 "내가 깬 것"을 구분할 수 없게 된다.

**⚠️ 6번에 브라우저 확인(§18-4)을 반드시 포함해라.** 이번 회차에 나온 결함 5건이 **전부
tsc·vitest·build를 통과한 상태**에서 브라우저에서만 드러났다(§13-5). 이 코드베이스는
자동 검증이 못 보는 영역이 넓다 — 캔버스 렌더·DOM 배선·판정 상수의 단위.

### 20-2. 이 코드베이스의 주석은 **문서다**

이 프로젝트의 주석은 "무엇을 하는가"가 아니라 **"왜 이렇게 됐는가"**를 담는다.
대부분 실제 사고·실측·되돌림 기록이며, 되돌리면 안 되는 이유가 적혀 있다.

특히 밀도가 높은 곳:

| 파일 | 담긴 것 |
|---|---|
| `src/combat/constants.ts` | 모든 밸런스 수치의 산출 근거와 조정 이력 (v1.5 하향의 산술) |
| `src/combat/stages.ts` | 경제 모델 전체와 게이트 역산 (⚠️ 단 §13-3의 드리프트 주의) |
| `src/position/trade.ts` | 세탁 차단 이력, 주식 수 가중 평균의 등가성 논증 |
| `src/position/constants.ts` | `GOLD_CONVERSION = 0.50`의 역산 근거 |
| `src/combat/mechanics.ts` | 개체별 독립 판정으로 바꾼 이유 |
| `src/app/stage-flow.ts` | click-path 결함 5건의 해법 |
| `src/sprites/render/composite.ts` | 스프라이트 합성 정책 · blit 금지 판별법 |

**"왜 이렇게 돼 있지?"라는 생각이 들면 그 파일의 주석을 먼저 읽어라.** 대개 답이 있다.

### 20-3. ★ 병렬 작업 규칙 (여러 에이전트를 동시에 돌릴 때)

이 세션에서 여러 에이전트를 동시에 돌렸고, **충돌 회피의 핵심은 하나였다**:

> **공개 시그니처를 바꾸지 않는다.**

| 규칙 | 이유 |
|---|---|
| **파일 소유권을 명시적으로 나눠라** | 한 파일을 두 에이전트가 편집하면 나중 쪽이 앞쪽을 덮어쓴다 |
| **계약 파일(`*/types.ts`)은 한 명만 소유한다** | 여러 모듈이 읽으므로 바뀌면 전부 깨진다. 바꿔야 하면 **먼저 그것만 하고 합류시켜라** |
| **필드를 추가할 때는 선택 필드(`?`)로** | `CombatState.skillCooldowns`·`boss`가 선택 필드인 이유가 정확히 이것이다 — 시뮬레이션 밖(`combat-fixtures.ts`)에서 리터럴을 만드는 곳이 있어 필수 필드를 늘리면 그 파일이 타입 에러로 깨진다 |
| **배럴(`index.ts`)은 마지막에 한 번만 정리해라** | 여러 에이전트가 동시에 export를 추가하면 충돌 지점이 된다 |
| **밸런스 상수는 한 명만 만진다** | 두 명이 각자 조정하면 시뮬레이터 결과의 원인을 분리할 수 없다 |
| **각자 자기 범위의 테스트를 돌리고, 합류 후 전체를 다시 돌려라** | 부분 통과가 전체 통과를 뜻하지 않는다 |

**권장 분할 예시 (§15 로드맵 기준)**

| 에이전트 | 소유 파일 | 겹치는 지점 |
|---|---|---|
| A: 튜토리얼 | `src/app/tutorial.*` | `stage-dom.ts`(마크업) · `stage.ts`(배선) — **마지막에 한 번에 합류** |
| B: 공개 연출 | `src/app/reveal.*` | 〃 + `session.ts`(청산 기록 노출) |
| C: 배포 | `.github/workflows/*` · `vite.config.ts` | 없음 — **완전 독립** |
| D: 날씨 배선 | `src/app/stage.ts`의 `drawBattle` 호출부 | A·B와 같은 파일 — **순서를 정해라** |

`stage.ts`와 `stage-dom.ts`는 거의 모든 새 화면이 거쳐 가는 병목이다.
**이 둘은 한 명이 소유하고, 나머지는 순수 함수 모듈만 만들어 넘기는 방식**이 가장 안전하다.

### 20-4. 커밋 규칙

```
<type>: <description>

<body — 왜 그렇게 했는지. 수치를 바꿨다면 근거와 실측을 반드시 남겨라>
```

타입: `feat` / `fix` / `refactor` / `docs` / `test` / `chore` / `perf` / `ci`

⚠️ **밸런스 수치를 바꿨다면 커밋 본문에 시뮬레이터 실측 결과를 넣어라.**
이 프로젝트의 밸런스 이력은 전부 그렇게 추적돼 있고, 그 기록이 없으면 다음 사람이
같은 값을 근거 없이 되돌린다.
